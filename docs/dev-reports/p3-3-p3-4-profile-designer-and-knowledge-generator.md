## 一、开发目标

### P3-3：Profile 设计器
通用 LLM 根据用户的任务描述，自动设计一个完整的 TaskProfile（域定义、节点类型、边类型、栏目、提示词、初始化策略）。

### P3-4：知识生成器
根据主题 + Profile，自动生成初始知识网络（节点、卡片、边），支持 MVP 先行和完整开发两种模式，含分布式子调用。

## 二、P3-3：Profile 设计器

### 2.1 设计思路

**怎么设计**：
- 输入：用户的任务描述（如"生成激光雷达技术路线知识网络"）
- 输出：完整的 `TaskProfile` 对象
- 流程：分 5 步 LLM 调用 → 校验+修复循环 → 输出 Profile 文件

**5 步设计流程**：
1. **域划分设计**：LLM 设计 3-8 个语义域和 3-5 个视觉分支
2. **类型系统设计**：基于基础 11 种节点类型 + 12 种边类型，可扩展主题特定类型
3. **栏目目录设计**：复用基础 13 个栏目，LLM 判断是否需要新增主题特定栏目
4. **提示词设计**：基于 FMCW 模板替换主题内容，含节点粒度硬约束
5. **初始化策略设计**：MVP vs 完整开发参数（根据域数量自适应）

**校验+修复循环**：
- 检查必填字段、域数量一致性、视觉分支一致性、域的 visualBranch 是否在列表中
- 不符合则让 LLM 修复，最多 3 轮
- 修复失败时记录 warning，不中断流程

### 2.2 为什么这样设计

1. **LLM 驱动设计适应不同主题**：不需要人工编写 Profile，用户只需描述任务
2. **参考 FMCW Profile 作为模板**：保证设计质量下限，避免从零设计的不确定性
3. **分步骤设计降低单次 LLM 调用复杂度**：避免输出截断，每步聚焦一个方面
4. **校验+修复循环保证输出符合契约**：不会出现无效结构化输出，这是 P0-P1 阶段的痛点
5. **基础类型系统作为共享底座**：11 节点+12 边+13 栏目所有 Profile 共享，主题只需扩展而非从零设计

### 2.3 交付物

| 文件 | 说明 |
|---|---|
| `server/profile/profile-designer.ts` | ProfileDesigner 类（5步设计+校验修复+写文件） |
| `app/api/profile/design/route.ts` | API 路由（POST /api/profile/design） |

### 2.4 API 接口

```
POST /api/profile/design
Body: {
  topic: string,              // 主题，如 "激光雷达技术路线"
  taskDescription: string,    // 任务描述
  writeToFile?: boolean       // 是否写入 profiles/<topic>.ts
}
Response: {
  profile: TaskProfile,       // 完整 Profile
  iterations: number,         // 修复迭代次数
  validationIssues: string[], // 未解决的校验问题
  warnings: string[],         // 警告信息
  filePath?: string           // 写入的文件路径
}
```

## 三、P3-4：知识生成器

### 3.1 设计思路

**怎么设计**：
- 输入：主题 + Profile + 模式（mvp/full）
- 输出：知识网络（节点、卡片、边）
- 流程：初始化 → ReAct 循环 → 分布式子调用 → 批量合并 → 收敛判断

**两种模式**：
| 模式 | 节点数 | 栏目 | ReAct 轮数 | 时间 |
|---|---|---|---|---|
| MVP | 15-30 | 只填 definition | 2-3 | 2-5 分钟 |
| 完整开发 | 80-150 | 5+ 栏目 | 6-24 | 25-40 分钟 |

**ReAct 循环**：
1. **Observe**：评估当前知识网络的覆盖度（域节点分布、核心栏目填充率）
2. **Act**：调用 LLM 生成一批新知识（节点、卡片、关系）
3. **批量合并**：按 id/名称去重节点，按 nodeId+type 去重卡片，按 source+target+type 去重关系
4. **收敛判断**：新增节点 < 2 或达到目标节点数时收敛

**分布式子调用**：
- 触发条件：gaps > 3 或 当前节点 > 30
- 拆分策略：按每组 2 个 gap 拆分，最多 2 组
- 执行方式：并行执行各组（生产环境应限制并发）
- 输入限制：graphIndex 精简至 50 节点（原 500）

**批量合并而非逐个查重**：
- 每批累积后统一合并，不要逐条调用图内查重工具
- 新增节点可引用本批或此前批次新节点 ID 作为父级
- 这是 P0-P1 阶段用户明确要求的优化

### 3.2 为什么这样设计

1. **MVP 先行让用户确认方向**：避免 30 分钟后发现完全错误，用户可通过 MVP 判断 Profile 设计与知识生成设计是否正确
2. **自适应 ReAct 机制保证知识网络完整性**：逐节点计数重置、预算自适应，直到新增知识收敛
3. **分布式子调用避免单次 LLM 调用超出 token 限制**：这是 P0-P1 阶段用户明确要求的优化（输出预算管理）
4. **批量合并而非逐个查重**：减少重复节点，提高效率，这是 P0-P1 阶段用户明确要求的优化
5. **复用 FMCW 的节点粒度硬约束**：一个节点一个概念，禁止多概念，problem 不混入解决方法，保证知识网络结构清晰
6. **Profile 驱动的生成**：节点类型、边类型、栏目都从 Profile 读取，不同主题使用不同配置

### 3.3 交付物

| 文件 | 说明 |
|---|---|
| `server/agent/knowledge-generator.ts` | KnowledgeGenerator 类（ReAct循环+分布式+批量合并） |
| `app/api/agent/generate/route.ts` | API 路由（POST /api/agent/generate） |

### 3.4 API 接口

```
POST /api/agent/generate
Body: {
  topic: string,                    // 主题
  profile?: TaskProfile,            // 自定义 Profile（优先）
  profileId?: string,               // Profile ID（当前仅支持 fmcw-radar）
  mode?: "mvp" | "full",           // 模式（默认 mvp）
  writeToFile?: boolean             // 是否写入文件
}
Response: {
  network: KnowledgeNetwork,        // 知识网络（nodes/cardBlocks/relations）
  mode: string,                     // 模式
  iterations: number,               // ReAct 迭代次数
  totalNodes: number,               // 总节点数
  totalCardBlocks: number,          // 总卡片块数
  totalRelations: number,           // 总关系数
  distributedCalls: number,         // 分布式子调用次数
  warnings: string[],               // 警告信息
  converged: boolean,               // 是否收敛
  filePath?: string                 // 写入的文件路径
}
```

## 四、迭代优化方案

### 4.1 如果 Profile 设计不好

| 问题 | 优化方案 |
|---|---|
| 域划分不合理 | 增加 FMCW Profile 作为 few-shot 示例；分步骤用户确认（域划分确认后再设计类型系统） |
| 节点类型/边类型不符合主题 | 增加主题特定的设计指南（如"技术路线类主题建议 5-7 个域"）；增加校验规则强度 |
| 提示词质量差 | 增加 FMCW 提示词作为模板；增加节点粒度约束的正例/反例 |
| 校验修复循环无效 | 从 warning 升级为 error 强制修复；增加修复次数上限（当前 3 次） |
| 输出截断 | 进一步拆分步骤（如提示词设计拆分为 react/ingest/review 三步） |

### 4.2 如果知识生成不好

| 问题 | 优化方案 |
|---|---|
| 节点数量不足 | 增加 ReAct 轮数上限（从 24 提升到 36）；降低收敛阈值（从 <2 改为 <1） |
| 节点质量差（多概念、名称过长） | 优化提示词，增加节点粒度约束的正例/反例；增加审查环节，过滤低质量节点 |
| 重复节点多 | 优化批量合并的去重逻辑（增加语义相似度去重）；增加节点名称规范化 |
| 栏目填充率低 | 增加核心栏目填充要求；在 ReAct 提示词中强调栏目填充 |
| 分布式子调用效果差 | 优化分组策略（按域分组而非按 gap 数量）；增加组间去重 |
| 生成时间过长 | 优化输入大小（graphIndex 精简）；增加早期停止条件（达到最小目标节点数且覆盖度 > 80%） |
| LLM 输出无效 JSON | 增加 JSON 格式校验+修复；增加输出示例（few-shot） |

### 4.3 通用优化方向

1. **增加 few-shot 示例**：在提示词中加入 FMCW 的完整示例，提高 LLM 输出质量
2. **增加用户确认环节**：MVP 后用户确认方向，域划分后用户确认，避免累积错误
3. **增加审查环节**：生成后自动审查节点粒度、栏目填充率、重复节点等
4. **增加后台任务支持**：完整开发模式（25-40 分钟）应使用后台任务，避免 HTTP 超时
5. **增加 Profile 缓存**：相同主题的 Profile 设计结果缓存，避免重复调用 LLM
6. **增加知识网络可视化**：生成后自动渲染知识网络，方便用户验收

## 六、风险与限制

1. **LLM 输出质量不稳定**：依赖 LLM 的理解和生成能力，可能出现无效 JSON、重复节点、多概念节点等问题
2. **完整开发模式超时**：25-40 分钟的生成时间超过 HTTP 超时限制，需要后台任务支持
3. **Profile 设计器的 LLM 调用次数多**：5 步设计 + 3 轮修复 = 最多 8 次 LLM 调用，成本较高
4. **分布式子调用的并行控制**：当前实现使用 Promise.all 并行执行，生产环境应限制并发数
5. **知识网络质量依赖 Profile 质量**：Profile 设计不好会直接影响知识生成质量
6. **缺少端到端测试**：由于需要 LLM API Key，自动化测试覆盖有限
