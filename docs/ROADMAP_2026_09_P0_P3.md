# 2026-09-04 需求、实施与验收计划

本文件的 P0–P3 是本轮优先级，不是旧文档的同名发布版本。P0–P1 本轮实施；P2–P3 必须在用户验收 P0–P1 后启动。保留 SVG 渲染、节点组件、主树列布局和左右栏交互。

## P0：交互可靠性与资料整理

1. 拖动回调捕获不可变的起始坐标及指针坐标，避免 React 延迟执行读取已清空 ref。
2. 删除知识卡片重复大标题、历史访问策略、内部确认策略等实现说明。保留用户需要的修改预览、进度、异常和确认操作。
3. 顶部设置同时提供模型配置和字号配置：超小、小、中、大、超大，每档两个字号，共十个独立 CSS 变量；默认 12/13/14/15/16/17/18/20/24/28 px，可调整 10–40px，浏览器持久化。
4. 后台任务由服务端拥有。浏览器仅创建任务和查询进度，切换节点、隐藏标签、刷新或关闭页面不取消模型请求；重新打开相同浏览器会话恢复任务和回答。服务进程关闭与页面关闭不同：服务重启后明确显示中断，保留研究检查点，不伪称完成。
5. "总结并补充知识"采集已完成对话，通过 Knowledge 整理、Review 审查、Build 预览，用户确认后写入节点或知识卡。普通问答不自动修改图谱。
6. 返回格式兼容：JSON/代码围栏/对象包装/标准字段别名，严格字段校验；遇到截断、空文本、错误转义、类型不匹配时将具体错误反馈模型，最多三次修复。有效批次落盘。语义 Review 格式失败也修复，最终失败时保留候选而不绕过审查。
7. 修正多个检索关键词被拼成整句匹配造成的假阴性；收集候选后批量比对、合并。

验收：重复拖动并在释放时切换焦点无异常；启动问答后切换节点/刷新仍可看到完整回答；设置十项字号均能影响相应文字且刷新保留；对话能生成可确认的卡片变更；错误返回可修复且不写入损坏数据。

## P1：逐节点自适应 ReAct

流程：

主题/当前节点 → 读取节点、卡片、邻域 → 模型判断开放问题与知识缺口 → 检索/生成一批实质知识 → 观察新增量、剩余缺口 → 调整当前节点预算 → 探索后续节点（重置计数） → 批量合并 → 独立语义审查 + 结构校验 → Build 预览 → 用户确认。

- 根节点研究目标至少25分钟，时间硬上限35分钟；同时有总调用和访问节点上限。不通过空等凑时间；若模型连续失败、没有可探索节点或触及预算，明确报告未完成。
- 稀疏图谱（少于20节点）每节点最少6轮、初始10轮、最多24轮；较完整图谱最少4轮、初始6轮、最多18轮。每批有较多新增时延长；连续两轮明确收敛且新增很少时结束该节点。
- 普通子节点任务最长12分钟；根任务最多360次模型调用、80个访问主题；普通任务按稀疏程度最多100/48次调用。修复调用计入预算。
- 可读取现有节点，也继续研究尚未提交的候选节点；保持稳定临时ID和父级引用，统一合并后转成正式ID。
- 节点与卡片分离：新节点携带定义、原理等多栏目卡片；允许父节点与子节点在同批创建；支持有方向的语义关系。更新保留原卡片内容。
- 外部接口支持 web_search 时进行来源检索；不支持时明确以模型知识扩展并保留待核验说明，不能把图内搜索冒充联网检索。
- 保存每批成果、已访问节点、调用数、停止原因；最终候选不因单批失败丢失。研究检查点与用户保存的三个版本互不替代。
- 开发期基准由开发助手作为 LLM 观察知识框架、判断缺口并编写候选，复用应用的候选契约、批量合并、结构审查及 Build，不使用用户 Key 做长时间生成。用户 Key 仅用于获准的短程诊断和功能验证。应用面向用户的在线根节点检索仍支持上述长时预算。

验收：通过真实模型记录访问节点及每节点轮次；有效新增多于旧2节点限制；在测试仓库验证新增节点能进入现有 SVG 同层列；混合旧/新父级无悬空；结构错误可反馈修复；产生最终可确认候选。不得保证任意外部模型永不输出非法JSON，保证非法结果不进入图谱且有效成果能保留。

## P2：特定任务类型专用适配器（优先级调整，P3 完成后按需选择）

> **优先级变更说明**：原 P2"多任务图谱迁移"已被 P3 插件化覆盖。P3 完成后，Profile 机制已支持任意主题的知识网络生成。P2 重新定位为"特定任务类型专用适配器"——针对需要特殊输入解析的任务类型开发专用适配器，在 P3 通用 Profile 机制之上提供领域特化能力。

### 当前图谱生成方法

图谱由主分类树、带类型的跨节点关系及节点知识卡组成。Knowledge 负责观察、找缺口与生成候选；Review 负责语义判断与确定性结构门禁；Build 把已审核候选变成可预览的事务；Development 管理任务、确认、持久化和版本。画布只投影数据，不负责决定知识含义。

### P2 专用适配器类型（P3 完成后按需选择，建议优先 CodeGraph）

| 适配器 | 输入 | 特殊解析需求 | 节点类型扩展 | 关系类型扩展 |
| --- | --- | --- | --- | --- |
| **CodeGraph**（优先） | 项目代码/算法代码 | AST 解析、符号提取、调用链分析、多输入数据流 | module、function、dataset、operator | CALLS、READS、WRITES、DEPENDS_ON、FLOWS_TO |
| 论文 PDF 结构解析 | 论文 PDF | 章节结构提取、公式抽取、引用关系解析、实验数据提取 | paper、method_contribution、experiment、finding | IMPROVES、ALTERNATIVE_TO、CITES、VALIDATED_BY |
| 需求文档解析 | 需求文档/PRD | 需求层级提取、接口定义、测试用例关联 | requirement、component、interface、test_case | IMPLEMENTS、DEPENDS_ON、COVERED_BY、VERIFIED_BY |

### CodeGraph 适配器设计（优先开发）

先用解析器确定文件、符号、调用与数据依赖，再让 LLM 解释算法设计和跨文件含义。支持多输入算子和有向循环，不把数据流强行解释为分类树；主树仍用来导航，跨边表达流动。代码问答需返回文件和行号，上传代码按不可信资料处理，不自动执行。

知识卡显示算法的设计概要或具体实现，图谱可对项目代码进行提问。整体交互页面架构和接入 LLM 的能力无需太多变化，仅是对用户上传/输入信息的理解与处理不一样。

交付顺序：TaskProfile 设计评审 → 代码输入与源码定位 → 多输入关系投影 → 基于源码问答 → 两类主题迁移回归测试。不得在本轮提前替换现有图形组件。

## P3：插件化方法沉淀——从"一个应用"到"一种可插拔的 LLM 能力"

> **优先级调整说明**：用户确认先完成 P3 再做 P2。P3 的核心是将当前 FMCW 知识图谱应用的构建过程沉淀为可插拔的通用 LLM 能力插件，由通用 LLM 根据生成任务对不同 Profile 进行设计和主题内容生成。FMCW 技术图谱作为第一个 Profile 指导通用 LLM 适配不同的任务主题。

### P3 启动前基准加固（已完成，提交 b45dd0c）

在启动 P3 之前，先对 FMCW 基准进行节点粒度硬约束加固，确保抽取的 Profile 本身包含正确的语义约束：

1. **节点类型合并**：phenomenon → problem（12 种→11 种）。problem 类型统一代表"一个问题或现象"。
2. **NODE_TYPE_SEMANTICS 常量**（schema.ts）：每种节点类型硬编码规定"只放一个什么"和"禁止什么"：
   - concept = 一个概念，禁止多个并列概念、方法、算法
   - method/algorithm = 一个解决方案，禁止多个并列方法、问题描述
   - problem = 一个问题或现象，**禁止混入解决方法或子问题**
   - model = 一个模型，parameter = 一个参数，metric = 一个指标
3. **提示词约束**（3 处 5 套提示词）：adaptive-research.ts ReAct 提示词 + ingest/route.ts 四套资料接入提示词，各新增节点粒度规则，含反例（"CV、CA、CTRV、CTRA"必须拆分）和正例（共性父节点+子节点）。
4. **确定性审查规则**（validation.ts，4 条 warning）：
   - `MULTI_CONCEPT_NODE`：名称含并列连词的粒度敏感类型节点
   - `NODE_NAME_TOO_LONG`：名称 >20 字
   - `SHORTFACT_TOO_LONG`：shortFact >80 字
   - `PROBLEM_NODE_HAS_SOLUTION`：problem 节点 shortFact 含方法/算法/解决等词

### 硬编码与 Profile 配置化的边界

P3-2 的核心工作是把**主题相关的硬编码**抽取为 Profile 配置，**主题无关的通用规则**保持共享：

| 硬编码内容 | 当前位置 | P3 后处理 | 原因 |
| --- | --- | --- | --- |
| 域数量 = 11 | validation.ts | **配置化**（Profile.validation.domainCount） | 不同主题域数量不同 |
| 具体域 ID 枚举（11 个） | schema.ts | **配置化**（Profile.domains） | 不同主题域名不同 |
| 视觉分支 = 5 | validation.ts | **配置化**（Profile.validation.visualBranchCount） | 不同主题可能需要不同分支数 |
| 根节点 = fmcw | 数据中 | **配置化**（Profile.rootNode） | 不同主题根节点不同 |
| 节点类型 11 种 | schema.ts | **半配置化**（基础类型共享 + Profile 可扩展） | 大部分通用，少数可扩展 |
| 边类型 14 种 | schema.ts | **半配置化** | 大部分通用，少数可扩展 |
| 栏目目录 14 个 | card-section-catalog.ts | **半配置化** | 大部分通用，少数可扩展 |
| **节点粒度 4 条规则** | validation.ts | **保持通用共享** | 主题无关，所有 Profile 共享 |
| 结构性规则（树/图/公式/卡片） | validation.ts | **保持通用共享** | 主题无关，所有 Profile 共享 |
| Agent Loop / ReAct / 批量合并 | adaptive-research.ts | **保持通用共享** | 主题无关，所有 Profile 共享 |
| 应用架构 / UI / SSE / 后台任务 | 各组件 | **保持通用共享** | 主题无关，所有 Profile 共享 |

**关键原则**：P3 不是重写应用，而是把"什么主题"从硬编码变为配置。应用架构、Agent Loop、审查框架、UI 组件全部复用，只有域定义、节点类型、提示词、根节点等主题相关内容从 Profile 加载。

### P3 分阶段计划

#### P3-1：插件骨架与契约（0.5-1 天）

**目标**：建立插件的目录结构、契约 schema 和基本文档，不动当前项目代码。

交付物：
- `plugin/` 目录骨架
- `plugin/SKILL.md`：插件说明（何时使用、输入要求、步骤、验证标准、生成产物、恢复方式）
- `plugin/plugin.json`：插件元数据（名称、版本、依赖、入口）
- 4 个契约 schema（TypeScript interface + JSON Schema）：
  1. `TaskProfile`：主题配置契约（域、节点类型、边类型、栏目、审查规则、提示词、根节点）
  2. `ResearchCandidate`：知识候选契约（新节点、卡片块、关系、证据）
  3. `MvpOutput`：MVP 输出契约（Profile 摘要 + 最小知识网络骨架 + 示例卡片）
  4. `PluginState`：插件状态契约（当前阶段、Profile、检查点、用户确认记录）
- `plugin/README.md`：插件安装和使用说明

**验收**：契约 schema 通过 TypeScript 编译；SKILL.md 包含完整的使用流程；目录结构清晰可扩展。

#### P3-3：Profile 设计器（LLM 驱动）（2-3 天）

**目标**：通用 LLM 根据用户的任务描述，自动设计一个完整的 TaskProfile。

工作流：
1. 用户输入任务描述（如"我要生成一个激光雷达技术路线知识网络"）
2. LLM 分析任务类型和主题，参考 FMCW Profile 作为模板
3. LLM 输出 Profile 设计草案：
   - 域划分（建议 3-5 个视觉分支，8-15 个域）
   - 节点类型（基础类型 + 主题扩展）
   - 边类型（基础类型 + 主题扩展）
   - 栏目目录（基础栏目 + 主题扩展）
   - 根节点定义
   - 提示词基础（复用通用提示词 + 主题追加）
4. 校验+修复循环：Profile 设计器自动检查 Profile 是否符合契约 schema，不符合则反馈 LLM 修复，最多 3 次
5. 输出完整的 `profiles/<topic>.ts` 文件

**验收**：
- 输入"激光雷达技术路线"能生成合理的 Profile（域划分、节点类型、根节点）
- Profile 通过契约 schema 校验
- 生成的 Profile 可以被 P3-2 的加载机制正常加载
- FMCW Profile 作为模板参考，新 Profile 结构一致

#### P3-4：知识生成器（LLM 驱动，含分布式生成）（2-3 天）

**目标**：根据主题 + Profile，自动生成初始知识网络。复用当前的自适应 ReAct 机制，但支持 Profile 配置。

工作流：
1. 加载 Profile，获取域划分、节点类型、栏目目录、提示词
2. 从根节点开始，按域划分生成一级域节点
3. 对每个域节点，调用自适应 ReAct 生成子节点（逐节点计数重置、预算自适应）
4. 批量合并而非逐个查重
5. 分布式子调用：当单轮 gaps>3 或 newNodes>8 时，拆分为多组降低单次负荷
6. 输出完整的初始知识网络（节点 + 卡片 + 关系）

**复用现有能力**：
- adaptive-research.ts 的自适应 ReAct 循环（逐节点计数重置、预算自适应）
- research-output.ts 的多格式兼容解析
- research-build.ts 的候选构建与关系去重
- background-jobs.ts 的后台任务管理
- 节点粒度 4 条审查规则（通用共享）

**验收**：
- 根据激光雷达 Profile 能生成 80-150 个节点的初始知识网络
- 节点符合"一个节点一个概念"约束
- 知识卡栏目完整（definition + principle + engineering_tradeoff 等）
- 关系合理（父子关系 + 跨节点语义关系）
- 生成过程支持后台任务，不阻塞 UI

### MVP 先行机制（P3 核心工程特性，用户确认）

插件生成新应用时，**不直接做完整的根节点深度检索**，而是分三阶段：

#### Phase 1：MVP 快速生成（2-5 分钟）

- 节点数：15-30 个（完整开发 80-150 个）
- 深度：根节点 + 一级域 + 每域 2-3 个核心概念（完整开发 DFS 全深度）
- 栏目：只填 definition（完整开发 5+ 栏目）
- ReAct 轮次：2-3 轮（完整开发 6-24 轮）
- 不调用 web_search，仅用模型知识
- Profile 设计：简化版 3-5 个域（完整开发 8-15 个域）
- 输出：MVP 知识网络骨架 + Profile 设计摘要 + 2-3 个示例卡片

#### Phase 2：用户确认与调整

- 展示给用户：
  1. Profile 设计（域划分、节点类型、根节点）
  2. MVP 知识网络骨架（节点列表 + 层级关系）
  3. 示例卡片（2-3 个完整卡片，展示知识粒度和质量）
- 如果用户不满意：
  - 说明当前设计的理由
  - 给出 3-5 个具体调整方向，每个方向包含：调整类型、具体操作、原因、预期效果
  - 例如："域划分过粗，建议将'信号处理'拆分为'波形生成'和'谱处理'两个域，预期效果是知识组织更精细"
  - 用户选择调整方向后，重新生成 MVP
- 如果用户满意：锁定 Profile 核心设计（域划分、节点类型、栏目、根节点），进入 Phase 3

#### Phase 3：完整开发（25-40 分钟）

- 基于锁定的 Profile 设计
- 节点数：80-150 个
- 自适应深度检索（逐节点 ReAct 计数重置、预算自适应、根节点 25-35 分钟）
- 完整知识卡（5+ 栏目）
- 批量合并 + 分布式子调用
- 应用构建验证交付

#### 锁定机制

- 用户确认 MVP 后，Profile 核心设计（域划分、节点类型、栏目、根节点）被锁定
- Phase 3 只完善知识内容，不改变核心设计
- 中途需要改变核心设计时，需重新走 MVP 流程（Phase 1 → Phase 2）
- 锁定状态记录在 PluginState 中，可追溯
